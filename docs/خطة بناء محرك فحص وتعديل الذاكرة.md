# خطة هندسية لبناء برنامج فحص وتعديل الذاكرة (Cross-Platform Memory Scanner & Debugger)

بناء أداة متكاملة لفحص وتعديل الذاكرة تعمل بكفاءة على نظامي **Windows** و **Linux** يتطلب معمارية تفصل تماماً بين واجهة المستخدم (GUI) وبين طبقة التعامل مع نظام التشغيل (OS Abstraction Layer).

---

## أولاً: الخطة الهندسية لبناء البرنامج (Cross-Platform Architecture)

لتحقيق أداء يضاهي سرعة Cheat Engine في فحص ملايين العناوين في أجزاء من الثانية، يجب بناء النواة بلغة قريبة من العتاد، مع استخدام إطار عمل مرن للواجهة.

### 1. التقنيات المقترحة (Tech Stack)
* **نواة المحرك (Core Engine):** لغة **Rust** أو **C++20**. 
  * *ملاحظة:* تعتبر Rust خياراً ممتازاً هنا لأنها تمنحك سرعة C++ مع حماية عالية عند التعامل مع تعدد الخيوط (Multithreading) وإدارة الذاكرة الخاصة بالبرنامج نفسه.
* **واجهة المستخدم (Frontend/GUI):**
  * **الخيار الأول (الأخف والأسرع):** استخدام **Dear ImGui** أو **Qt6 (C++)** لبناء واجهة أصلية (Native) سريعة جداً في عرض الجداول الضخمة (Virtual Lists).
  * **الخيار الثاني (عصري وسهل التخصيص):** استخدام **Tauri (Rust + React/Vue)**، حيث يعمل Rust في الخلفية ويتواصل مع واجهة ويب خفيفة جداً (أخف بكثير من Electron).
* **مكتبات التفكيك والترجمة (Disassembly & Assembly):**
  * مكتبة **Capstone** لتفكيك الكود (Disassembler) وتحويل الـ Machine Code إلى Assembly.
  * مكتبة **Keystone** أو **LLVM** لتجميع الكود (Assembler) لحقن التعليمات البرمجية.

### 2. طبقة تجريد النظام (OS Abstraction Layer - HAL)
هذه أهم نقطة في المشروع لأن طريقة قراءة الذاكرة تختلف جذرياً بين النظامين:

| الوظيفة | نظام Windows | نظام Linux |
| :--- | :--- | :--- |
| **تحديد مناطق الذاكرة (Memory Regions)** | دالة `VirtualQueryEx` لمعرفة الصفحات المحجوزة وصلاحياتها (قراءة، كتابة، تنفيذ). | قراءة وتحليل ملف `/proc/$PID/maps` نصياً لمعرفة خريطة الذاكرة الخاصة بالعملية. |
| **قراءة وكتابة الذاكرة (Read/Write)** | استخدام `OpenProcess` ثم `ReadProcessMemory` و `WriteProcessMemory`. | استدعاء النظام المباشر `process_vm_readv` و `process_vm_writev` (أسرع من `ptrace`)، أو عبر `/proc/$PID/mem`. |
| **التنقيح وتتبع الكود (Debugging)** | استخدام Windows Debugging API أو Vectored Exception Handling (VEH). | استخدام `ptrace` للتحكم في مسار العملية ووضع نقاط التوقف (Hardware/Software Breakpoints). |

### 3. مراحل التنفيذ (Roadmap)
1. **المرحلة الأولى (CLI Scanner):** بناء أداة سطر أوامر قادرة على الاتصال بعملية (PID)، قراءة خريطة الذاكرة، والبحث عن قيمة صحيحة (Exact Value Int32) وتعديلها على النظامين.
2. **المرحلة الثانية (تحسين الأداء - Optimization):** 
   * إضافة تعدد الخيوط (Multithreading) لتقسيم صفحات الذاكرة على أنوية المعالج.
   * استخدام تعليمات **SIMD (AVX2/SSE)** لمقارنة مصفوفات البايتات بسرعة فائقة.
   * ضغط نتائج البحث المؤقتة في الرام أو القرص باستخدام خوارزمية سريعة مثل **LZ4**.
3. **المرحلة الثالثة (الواجهة والـ Pointer Scanner):** بناء الواجهة الرسومية، وإضافة ميزة تجميد القيم (Freeze)، وبناء خوارزمية البحث عن المؤشرات الثابتة (Multi-level Pointers).
4. **المرحلة الرابعة (الـ Debugger ومحقن الكود):** دمج مكتبة Capstone لعرض الـ Assembly، وإتاحة معرفة "ما الذي يقرأ أو يكتب في هذا العنوان" عبر Hardware Breakpoints.

## ثانياً: أحدث مميزات Cheat Engine (الإصدارات الأخيرة 7.5 - 7.7)

شهد Cheat Engine تطورات كبيرة مؤخراً نقلته من مجرد أداة تعديل ذاكرة إلى بيئة هندسة عكسية متكاملة:

* **مترجم C و C# مدمج (Inline C & C# Compiler):** بدلاً من كتابة سكربتات الحقن بلغة Assembly المعقدة أو Lua فقط، أصبح بالإمكان كتابة كود C مباشرة داخل بلوك `{$CCODE}` أو `{$C}` ليقوم البرنامج بترجمته وحقنه في اللعبة مباشرة.
* **دعم عميق لمحركات الألعاب (.NET / Mono / Unreal Engine):** تحسينات ضخمة في أداة `.NET Info` تسمح بعمل Detour (تحويل مسار) للدوال بضغطة زر واستدعاء الدوال (Invoke methods) مباشرة، بالإضافة إلى دعم تحليل هياكل البيانات (Structure Dissect) الخاصة بمحرك Unreal Engine.
* **Speedhack بدون حقن DLL:** تطوير آلية تسريع أو إبطاء الألعاب لتعمل بدون الحاجة لحقن ملفات DLL خارجية يسهل كشفها، مع توافقية أعلى مع ألعاب Unity بدون الحاجة لإيقاف الـ VSync.
* **دعم GDB Server وبنية ARM64:** إضافة واجهة اتصال عبر `gdbserver` مما يسهل الاتصال بالمحاكيات وأجهزة اللينكس والأندرويد عن بُعد، مع دعم تلوين وتفكيك معمارية ARM64 وميزة تجاهل البايت العلوي للمؤشرات (ARM Memory Tagging).
* **تحسينات البحث (AOBSCANEX & Wildcards):** أمر `AOBSCANEX` للبحث في الذاكرة القابلة للتنفيذ فقط لتسريع تفعيل السكربتات، ودعم المعاملات المنطقية (أكبر من / أصغر من) داخل البحث الست عشري (Hex).
* **مشاركة الجداول (CEShare) ودعم الإضافات:** تنظيم مجلد خاص للإضافات (Extensions) مع بداية دمج أدوات مساعدة لتحليل الكود، وتطوير منصة مشاركة الجداول المجتمعية داخل البرنامج.

## ثالثاً: كيف يمكنك تطوير برنامجك ليتفوق على Cheat Engine؟

رغم قوة Cheat Engine، إلا أنه يعاني من كود قديم مبني بـ Lazarus/Delphi وواجهة مزدحمة ومعقدة للمبتدئين، بالإضافة إلى ضعف دعمه الأصلي للينكس مقارنة بويندوز. يمكنك التميز عبر النقاط التالية:

### 1. دعم أصلي (First-Class Support) لألعاب Proton و Wine على لينكس
أغلب لاعبي لينكس اليوم يشغلون ألعاب ويندوز عبر Proton (مثل أجهزة Steam Deck). الأدوات الحالية على لينكس (مثل *PINCE* أو *scanmem*) تعاني أحياناً في التعامل السلس مع بيئة Wine. إذا جعلت برنامجك يكتشف تلقائياً عمليات Wine/Proton ويترجم مسارات الذاكرة والـ Symbols الخاصة بـ Windows PE داخل لينكس بسلاسة، فستمتلك ميزة تنافسية ضخمة.

### 2. محرك سكربتات Python و JavaScript بدلاً من Lua
استخدام **Python** (أو JS/TypeScript) كلغة برمجة للسكربتات داخل برنامجك (أشبه بمكتبة Frida) سيجذب قاعدة ضخمة من المطورين الذين يفضلون Python على Lua، مع إمكانية استخدام مكتبات Python لتحليل البيانات وأتمتة العمليات.

### 3. بنية (Client-Server) للعمل عن بُعد بشفافية
تصميم النواة كـ خادم خفيف (Headless Daemon) يعمل على الجهاز الهدف، والواجهة الرسومية كعميل يتصل به عبر Socket. هذا يسمح بـ:
* تشغيل الواجهة على جهاز، وفحص لعبة تعمل على جهاز آخر أو على Steam Deck أو هاتف أندرويد.
* تقليل احتمالية رصد الواجهة الرسومية من قبل أنظمة الحماية البسيطة.

### 4. تمثيل بصري لهياكل البيانات (Node-based Structure Visualizer)
استبدال نافذة Structure Dissect النصية المعقدة في CE بواجهة رسومية تفاعلية (Nodes & Graphs) تشبه برنامج *ReClass.NET*، بحيث يرى المستخدم المؤشرات (Pointers) وهي تتفرع بصرياً في الوقت الفعلي.

### 5. دمج مساعد ذكاء اصطناعي محلي (Local LLM Decompiler)
دمج نموذج لغوي صغير أو ربط عبر API يقوم بقراءة دالة الـ Assembly التي توقفت عندها اللعبة، وتحويلها فوراً إلى كود C++ مقروء مع شرح وظيفة الدالة (مثل: *"هذه الدالة تقوم بخصم نقاط الصحة بعد حساب الدروع"*) واقتراح كود الـ Injection المناسب تلقائياً.

### 6. نظام تحكم بالإصدارات للجداول (Git-Friendly Tables)
حفظ جداول البحث بصيغة **JSON** أو **YAML** نظيفة ومقروءة بشرياً بدلاً من صيغة XML المعقدة الخاصة بـ `.CT`، مما يسهل على المطورين رفعها على GitHub وعمل Diff و Merge للتعديلات.
